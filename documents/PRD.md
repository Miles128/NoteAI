# NoteAI PRD — AI 原生个人知识库

**版本**：v3.8
**日期**：2026-07-18
**状态**：当前产品定义（唯一有效 PRD）

> 本文件是 NoteAI 唯一有效的产品需求文档。历史方案仅可存放在 `docs/archive/`，不得作为功能范围、架构决策或开发优先级的依据。

---

## 1. 产品定位

**一句话**：AI 帮你整理、编译、管理知识库，你只管丢资料进去。

**目标用户**：不想费劲整理、也不想从零开始的知识工作者。

**灵感**：Karpathy LLM Wiki — Stop re-deriving, start compiling.

**与竞品的区别**：
- Obsidian + ChatGPT = 两套系统，每次提问从零开始
- NoteAI = 采集 → 整理 → 编译 → 操作，一站式闭环

---

## 2. 核心循环

```
丢资料 → AI 整理(分类/标签/链接) → AI 编译(综述/WIKI) → CLI agent 操作
```

三大支柱：

| 支柱 | 职责 |
|---|---|
| **整理** | 自动分类、标签提取、双向链接发现 |
| **编译** | 综述生成/级联更新（阅读层 + RAG 索引层双重用途） |
| **CLI Agent** | 执行文件操作（移动、创建主题、归档） |

RAG 定位为辅助检索，不是核心支柱。

---

## 3. 关键架构决策

| 项 | 决策 |
|---|---|
| 三层架构 | 保留 Notes / wiki / Raw |
| 主题事实来源 | `Notes/` 文件夹结构；`wiki/WIKI.md` 是自动生成的索引，不反向定义主题 |
| wiki 定位 | AI 编译层；主题综述是当前主视图，概念页、实体页等语义物化视图按阶段启用 |
| 语义编译 | Notes 为不可变源稿；先编译为带证据的语义 IR，再生成 Wiki 与查询索引 |
| 语义事实存储 | SQLite 保存文档块、概念、实体、命题、证据、关系和依赖；zvec/BM25 仅作查询索引 |
| Ingest pipeline | 保留总开关，默认**开**；关闭后仅手动触发 |
| 综述生成 | 批量入库结束后**后台异步**生成，UI 提示「正在生成」 |
| RAG vs CLI | 分离，不合并意图路由 |
| L1 用户画像 | 保留，仅用于理解用户背景，不作为知识库证据 |
| L2 会话上下文 | 仅携带当前会话最近 6 条消息；不持久化、不自动提炼、不形成长期人格记忆 |
| 云盘同步 | 保留入口，明确标记为实验功能 |
| RSS | 保留订阅与手动拉取，不启动后台轮询 |

### 5.1 P0 验收标准

- 新安装时 Ingest 总开关为开启状态，关闭后文件变化不会自动启动 Ingest。
- L1 仅从当前工作区 `.ai_memory/user_profile.json` 的 `profile_md` 读取，作为理解背景，不生成或改写画像。
- L2 每次请求最多携带当前会话最近 6 条消息，不写入 `.noteai/memory/`，不调用 LLM 做摘要或用户信息提取。
- RAG 返回知识回答与引用，不暴露移动、创建、归档等文件操作工具；文件操作由 CLI Agent 执行。
- 云同步入口始终带「实验」标识。
- Sidecar 启动后不创建 RSS 定时器；RSS 导入、订阅和“拉取全部”只能由用户点击触发。
- 已安装并选中的 CLI Agent 显示为可直接执行，不再出现“执行通道尚未接入”。

## 6. 划词智能检索（已实现）

用户在笔记中选中词句或段落后，可从浮动工具条发起解释、知识库检索、笔记搜索或联网搜索，不打断阅读与写作。

### 6.1 用户体验

选中文本后，在选区附近显示极简浮动工具条：

| 动作 | 行为 |
|---|---|
| 问知识库 | 先流式输出 LLM 快速解释；再由 LLM 自动决定是否补本地知识库或联网证据 |
| 搜笔记 | 打开本地全文搜索 |
| 联网搜索 | 强制走联网检索，Bing 优先，失败时回退 DuckDuckGo、Baidu |

快速解释不声明为已验证结论；后续的“知识库补充”带本地引用，“联网补充”带可点击网页来源。

### 6.2 产品边界

- 划词功能只负责解释、查找、补充背景。
- 不自动写回当前笔记。
- 若要插入结果，必须显式点击「插入当前位置」或「追加为补充说明」。
- 文件移动、创建、归档等操作继续交给 CLI Agent。
- RAG 仍然只做「问知识库并给引用」，不做文件操作。

### 6.3 查询构造与路由

选中文本较短时，必须带当前段落上下文，避免短词误检索。

```
选中文本：{selection}
所在笔记：{current_file}
上下文：{paragraph_context}

请先简洁解释选中文本；随后可按上下文自动补充本地知识库或联网证据。
```

自动路由由 LLM 意图分类完成；用户仍可通过“联网搜索”手动覆盖路由。选区长度限制为 2–800 字，优先传递选区所在段落与当前文件。

## 7. 统一 Inbox（已实现）

统一 Inbox 复用既有任务与失败队列，不创建第二份待办数据。它按优先级聚合：

1. 未完成、取消、失败或中断的 ingest；
2. 综述生成失败与文件转换失败；
3. 主题与链接待确认；
4. 知识库健康检查项。

每项携带稳定类型、优先级和可执行动作。转换失败与综述失败支持逐项重试或忽略；非运行中的 ingest 支持重试。首页与标题栏同步展示待处理计数。

首页、Inbox 与标题栏的状态查询必须是只读快照：不得同步执行全库断链修复、错位扫描、文件移动或索引重建。维护动作进入可去重的后台任务；大工作区中状态 RPC 应在 2 秒内返回。后台请求失败必须在对应界面转成可理解的状态提示，不得产生全局未处理 Promise rejection。

主题错位待办采用阈值自动处理：刷新 Inbox 或待办计数前，系统使用当前内容重新计算错位建议；紧邻的重复计数请求应去重，避免反复全库扫描。修改阈值、运行健康检查或执行入库流程时不受该去重限制。当建议分数大于或等于用户设置的自动分类阈值，且自动分类总开关开启时，立即移动笔记、更新 frontmatter、同步 WIKI，并异步更新迁移前后主题的综述。低于阈值的错位建议继续进入 Inbox，供用户直接选择“移到建议主题”或“留在当前主题”。显示分数必须使用实际判定分数，不使用四舍五入后的百分比参与比较。

阈值自动处理仅适用于可回退的主题移动。内容合并、主题合并、删除原笔记、冲突处理、转换失败和综述失败不得因分数高而自动执行。

RSS 与网页采集尚不进入 Inbox，待采集能力完成去重、来源追踪与人工确认后再独立接入。

## 8. RAG 引用完整性

- 普通 AI 对话默认进入工作区 RAG；联网仅由用户显式触发，不使用 LLM 将 chat/general 静默分流到无检索回答。
- 当前打开笔记仅作为向量检索候选，与其他笔记共同排序；只有进入最终证据集时才可引用。
- 可引用来源从 `[1]` 连续编号。回答页只显示正文中实际出现且编号有效的来源，不将候选资料伪装成已引用来源。
- 主题综述、关联笔记等扩展上下文不作为直接证据或引用来源。
- 每个由资料支撑的事实或结论必须紧随有效编号；知识库没有直接证据时应明确说明。

## 9. 智能整合与 Chunk 相似度地图（v3.2）

### 9.1 产品目标

系统自动发现重复、重叠或高度相关的笔记与主题，将可解释的候选送入统一 Inbox。AI 只在用户明确发起时生成整合稿或主题名称；默认不删除原笔记。

### 9.2 笔记合并候选

候选发现不调用 LLM，复用现有 Chunk 与 embedding，使用两条独立规则：

1. **内容重叠规则**：Chunk 两两余弦相似度不低于 `0.86`，且较短笔记至少 `60%` 的 Chunk 在另一篇存在匹配。
2. **语义相关规则**：标题相似度不低于 `0.82`；主题相同或主题相似度不低于 `0.85`；内容 Chunk 综合相似度不低于 `0.68`；最终综合分不低于 `0.76`。

综合评分权重：内容相似度 50%、标题相似度 25%、主题相似度 15%、Chunk 覆盖率 10%。设置默认提供“保守 / 平衡 / 积极”三档，高级设置可调整具体阈值。

相似笔记先聚成候选组，避免生成大量两两重复项。一次最多整合 5 篇，用户可以从候选组中取消笔记。候选项必须展示触发原因、匹配 Chunk、覆盖率和综合分。

### 9.3 合并与删除安全边界

- 候选只自动进入 Inbox；用户点击“审阅合并”后才调用 LLM 生成整合稿。
- 默认生成新整合稿并保留全部原笔记。
- 删除授权仅对本次合并有效，不提供长期全局自动删除开关。
- 删除前逐篇展示文件名并二次确认，优先移入系统废纸篓，不做不可恢复删除。
- Chunk 分为重复、互补和冲突：重复内容保留更完整表达，互补内容按章节合并，冲突内容同时保留并标注来源。
- 检测到日期、数字、结论或否定关系冲突时，整合稿标记“存在待确认冲突”；冲突处理完成前禁止删除原笔记。
- 整合稿保存逐段来源映射。

### 9.4 相似主题整合

主题候选要求名称语义相似度不低于 `0.88`，且两边笔记内容聚类相似度不低于 `0.72`。主题相似不能直接触发笔记内容合并。

主题合并流程：

1. 候选进入 Inbox，用户发起审阅。
2. LLM 读取主题名、综述与代表性 Chunk，提供 3 个新主题名及命名理由。
3. 用户选择或编辑新名称，预览迁移笔记、同名冲突与受影响综述。
4. 用户确认后更新目录、frontmatter、WIKI、索引与综述。
5. 两个旧主题名写入 `.noteai/topic_aliases.json`，统一映射到新主题。
6. 同名文件不覆盖，进入逐项冲突处理；旧目录清空后才删除。

### 9.5 全库 Chunk 相似度地图（后期 Pending）

本节仅保留后期产品定义，不进入 v3.2 当前开发范围。当前版本仅允许在智能合并候选扫描内部使用 Chunk 相似度，不提供全库关系图、距离画布、相似度矩阵或分层可视化入口，也不得在应用启动时构建关系图。

所有 Chunk 参与关系计算，但不绘制全量两两连线。每个 Chunk 默认仅保留 Top 6 近邻，并过滤低于阈值的边。

- 主题层：默认视图，展示知识簇、孤岛和主题间距离。
- 笔记层：放大主题或选择主题后展开笔记节点。
- Chunk 层：继续放大或选择笔记后展开 Chunk；点击节点显示原文、所属笔记、章节、距离和相似 Chunk。
- 支持网络图与相似度矩阵。
- 节点距离表达余弦距离，连线粗细表达相似度。

关系图独立保存为可续跑的稀疏图。入库时只更新新增或变化 Chunk 的近邻；删除或移动时同步处理节点。启动只校验版本与文件指纹，不重新计算全图。模型、Chunk 规则或参数变化时提示用户手动重建。

### 9.6 界面与视觉系统

应用保持本地知识库最直接的目录 / 笔记列表 / 正文三栏结构，不再增加“资料 / 阅读 / 关系”工作模式分栏。关系图继续使用独立图标入口，AI 面板按需展开。Inbox 保留顶部待办图标与数量徽标；点击后必须从首页、阅读、编辑或关系界面稳定切换到完整待办内容页，不增加文字入口。

视觉继续使用现有蓝色作为主要操作强调色；整理重点是减少无效装饰、统一间距和交互状态，而不是更换品牌色或隐藏核心导航。保留浅色、深色、纸张、跟随系统四种主题及清晰键盘焦点。

### 9.7 性能与验收标准

- 后期 Chunk 图目标支持至少 10,000 个 Chunk、每个 Top 6 近邻；该指标不作为 v3.2 当前版本发布门槛。
- 合并候选扫描不调用 LLM；只有生成整合稿和主题命名时调用。
- 任何原笔记删除都必须存在本次操作的一次性授权记录。
- 人工标注测试集中，进入 Inbox 的合并候选准确率目标不低于 85%。
- 四种主题下三种工作模式、Inbox、编辑器和关系图均可读可操作。

## 10. 语义知识编译器（v3.3）

### 10.1 问题陈述与成功定义

当前“编译”主要是清理转换后的 Markdown，并按主题直接生成综述。系统缺少稳定的语义中间层，导致综述中的结论难以精确追溯、修改或删除来源后难以可靠撤销旧结论，也无法只重建真正受影响的产物。

语义知识编译器将 `Notes/` 视为不可变源稿，将其编译为带证据的语义中间表示（SKIR），再物化为主题状态、Wiki 页面与查询索引。成功标准：

- 正式语义命题的源证据覆盖率为 100%。
- Wiki 中由资料支撑的实质结论可追溯到 `Notes/` 的稳定文档块。
- 单篇笔记变化只失效受影响的语义节点、主题状态和物化视图，不触发无关主题重编译。
- 删除来源后，无剩余证据支持的命题不得继续出现在正式物化视图中。
- 任一编译阶段失败时保留上一版可用产物，并可在下次 Ingest 中续跑。

### 10.2 输入与输出契约

输入：

- `Notes/**/*.md` 正文、规范 frontmatter 和主题文件夹路径。
- 可选的原件来源、页码、URL、日期等可追溯元数据。
- `schema.md` 与 `.ai_memory/project_rules.md` 中的工作区规则。

输出：

- `.noteai/compiler/semantic.db`：文档、稳定块、概念、实体、命题、证据、关系、依赖和编译运行记录。
- `.noteai/compiler/manifest.json`：编译器版本、Schema 版本、输入哈希和最近成功构建。
- `wiki/*_综述.md`：由主题状态物化的现有兼容视图。
- 后续阶段可选的 `wiki/concepts/`、`wiki/entities/`、比较页和开放问题页。
- RAG 使用的文档块索引与后续命题索引；索引不是语义事实来源。

### 10.3 SKIR 最小模型

Phase 1 固定支持以下对象，不允许模型自由扩展类型：

| 对象 | 含义 | MVP 是否物化页面 |
|---|---|---|
| Document | 一篇源笔记及其版本 | 否 |
| Block | 标题下的段落、表格或代码块 | 否 |
| Topic | 来自 Notes 文件夹的主题 | 生成主题综述 |
| Concept | 可复用的知识概念 | 仅入库 |
| Entity | 人物、组织、产品、模型、协议等 | 仅入库 |
| Claim | 作者基于材料得出的结论性判断或明确提出的假设 | 进入 TopicState |
| Evidence | Claim 到源 Block 的证据边 | 否 |

关系类型固定为 `IS_A`、`PART_OF`、`RELATED_TO`、`USES`、`SUPPORTS`、`CONTRADICTS`、`COMPARES_WITH`、`CAUSES`、`PRECEDES`、`APPLIES_TO`、`DEFINED_BY`、`MENTIONED_IN`。Phase 1 仅要求实现 `MENTIONED_IN`、`SUPPORTS` 和主题归属；其他关系按后续阶段启用。

每个正式 Claim 必须包含：规范化陈述、适用范围、`conclusion` 或 `hypothesis` 类型、抽取置信度、至少一个 Evidence、来源文档 ID 和来源块 ID。置信度表示抽取可靠程度，不表示命题为真的概率。

Claim 层只保存具有知识判断价值的内容：

- `conclusion`：作者明确得出的评价、比较结论、因果判断、趋势判断、预测、推荐或由前文推导出的结论；
- `hypothesis`：作者明确提出、尚待验证或带条件成立的假设、推测和研究命题。

以下内容即使真实、可引用，也不得生成 Claim 或 Evidence：定义与术语解释、产品属性、日期数字、普通事实罗列、背景介绍、命令及参数说明、API/配置说明、安装步骤、操作指引、示例、代码行为复述和标题改写。这些信息继续保留在 Block、Concept、Entity 与全文检索层。Evidence 只为通过上述类型门禁的 Claim 创建，不把“有原文依据”误等同于“值得成为命题”。

### 10.4 编译数据流

```text
Scan → Normalize → Parse → Semantic Extract → Resolve → Link
     → Topic Reduce → Materialize → Index → Validate → Publish
```

- Scan：用内容哈希识别新增、修改、移动和删除。
- Normalize：确定性规范化，不使用 LLM 改写 Notes 正文。
- Parse：生成带稳定 ID 的文档块。
- Semantic Extract：按块或章节输出受 JSON Schema 约束的语义对象。
- Resolve：处理别名、同义概念和已存在对象匹配；不确定项进入审核队列。
- Link：建立语义对象与证据、文档、主题的受控关系。
- Topic Reduce：把当前有效语义对象聚合成 TopicState，不直接写长文。
- Materialize：从 TopicState 生成兼容的主题综述和后续语义页面。
- Index：构建面向检索的派生索引。
- Validate：运行证据、引用、依赖和 Schema 质量门禁。
- Publish：事务提交数据库并原子替换文件产物；失败时保留上一成功版本。

### 10.5 稳定身份与增量失效

- `document_id` 由工作区内规范相对路径生成；文件移动通过内容哈希和显式迁移记录保持身份。
- `block_id` 由文档 ID、结构路径、块类型和规范内容摘要生成。
- 语义对象使用类型、规范名称和消歧键生成稳定 ID。
- 每个物化视图记录其输入节点与哈希，形成 `Note → Block → Semantic Object → TopicState → View/Index` 依赖链。
- 修改时只重编变化块；删除时先撤销其 Evidence，再清理无证据 Claim，最后沿依赖图重建受影响视图。

### 10.6 失败模式与降级

| 失败 | 行为 |
|---|---|
| LLM 未配置或暂时不可用 | 完成结构解析并标记语义抽取待处理；现有 RAG 和 Wiki 继续可用 |
| LLM 输出不符合 Schema | 尝试一次结构修复；仍失败则记录块级失败，不写入正式语义对象 |
| 单块抽取失败 | 其他块可继续，文档状态为 partial，主题视图默认不消费失败块的新结论 |
| 数据库事务失败 | 整次语义发布回滚，保留上一成功构建 |
| Wiki 物化失败 | 保留旧文件，记录可重试失败到统一 Inbox |
| 文件在编译中再次变化 | 当前结果因输入哈希不一致而丢弃，下轮重新编译 |
| 删除来源 | 撤销证据；无证据命题失效，不保留为知识事实 |

### 10.7 安全和产品边界

- 编译器不得改写 `Notes/` 正文；现有转换清理若需要写回，仍属于导入转换流程且必须保留来源。
- 用户画像只帮助理解术语，不可生成 Claim 或 Evidence。
- LLM 生成的综合推论必须标记为推论，并保留其依赖 Claim 列表，不能伪装成源资料事实。
- Phase 1 不自动生成实体页、不构建全连接图、不提供自动删除、不静默合并低置信度实体。
- RAG 回答仍优先引用 Notes 源块；Wiki 和 TopicState 可用于组织上下文，但不能成为唯一事实证据。
- Claim 类型必须由受控枚举校验；缺少类型、类型不受支持或属于事实/说明/指令的候选一律拒绝入库。
- Claim 抽取策略版本升级时，旧策略生成的 Claim/Evidence 作为派生数据失效并重新抽取；不得保留旧噪声，也不得修改 Notes 原文。
- Claim/Evidence 提供独立增量编译通道与独立块状态。执行“仅重编命题和证据”时，不重新抽取、不覆盖、不失效 Concept、Entity 及其来源关系。

### 10.8 分阶段范围

**Phase 1：可追溯编译 MVP**

- SQLite Schema、编译 Manifest 和事务边界。
- Markdown 稳定块解析与内容哈希。
- Concept、Entity、Claim、Evidence 的结构化抽取和校验。
- TopicState 聚合及现有主题综述的可追溯输入包。
- 语义阶段接入 Ingest，支持关闭、失败续跑和旧功能降级。

**Phase 2：依赖图与精确增量编译**

- 块级 Diff、删除证据回收、依赖失效传播、原子文件发布和构建快照。

**Phase 3：语义 Wiki**

- 经质量门禁后按需启用概念页、实体页、方法比较、冲突与开放问题页面，以及人工审核队列。

**Phase 4：Graph-RAG**

- 查询意图规划、文档块/Claim/Concept/Topic 多索引路由和受控图邻域扩展。

### 10.8.1 Phase 3 首个交付：主题语义页

- 主题语义页物化到 `wiki/semantic/{主题路径}/{末级主题}_语义.md`，不覆盖既有 `wiki/*_综述.md`。
- 页面只消费活跃 Claim 与活跃 Evidence；`hypothesis` 必须显式标记为待验证假设。
- 含有明确关联待审阅冲突的 Claim 暂不发布；不得用语义相似度或命题文本猜测冲突关联。
- 每项内容必须链接回来源 Notes 和标题路径；页面由 TopicState 派生，不能作为 RAG 的唯一事实证据。
- 工作台支持无副作用预览和显式发布；发布采用原子替换，失败时保留旧页。
- 本切片不自动发布 Concept/Entity 页面，不生成方法比较、开放问题页，也不自动裁决冲突。

### 10.9 Phase 1 验收标准

- 同一未修改文档重复编译得到相同的 Document/Block ID，且不会新增重复记录。
- 修改一个块时，未修改块的 ID 和语义对象保持稳定。
- 数据库中不存在没有 Evidence 的正式 Claim。
- 数据库中不存在定义、命令说明、参数解释、操作步骤、普通事实陈述等伪 Claim；正式 Claim 仅来自 `conclusion` 或 `hypothesis`。
- Claim 策略升级后，旧 Claim/Evidence 自动失效；重新编译不会把旧策略数据与新策略结果混合展示。
- Claim-only 全库编译只写 Claim、Evidence、Claim mention 与 Claim extraction 状态；编译前后的 Concept/Entity 数量及 mention 必须保持不变。
- Evidence 可以解析到存在的 Notes 文件和 Block；源文件内容哈希变化后旧证据不会被误当作当前证据。
- LLM 缺失、超时、非法 JSON、单块失败、数据库写失败均有自动化测试覆盖。
- 语义编译失败不阻止现有分类、RAG 文档索引和 WIKI 同步完成。
- Ingest 状态报告语义编译的文档数、块数、Claim 数、失败数和待处理数。
- `uv run pytest` 全量通过，且新增语义编译单元测试与至少一个 Ingest 集成测试。

### 10.10 语义关系工作台（v3.6）

语义编译结果必须提供可见、可审阅的桌面工作台，避免语义数据库成为只能由后台消费的黑盒。工作台直接复用目录 / 笔记列表 / 正文三栏，不在正文区域内再嵌套一套三栏，也不替代现有关系图。

左一在同一导航栏中同时显示文件夹树和四个常驻语义一级类别；左二根据左一选择，在普通笔记列表与当前语义类别的对象列表之间切换；右侧相应显示笔记正文或语义对象详情与来源证据：

1. 实体与概念；
2. 命题与证据；
3. 冲突；
4. 双向链接。

“实体与概念”在左二顶部提供实体 / 概念二级切换，不额外占用左一一级类别。未选择列表项时，右侧显示当前类别的覆盖度、数量和使用说明。

工作台固定包含以下数据：

| 视图 | 内容与动作 |
|---|---|
| 概览 | Document、Block、Concept、Entity、Claim、Evidence 数量，编译状态与最近更新时间 |
| 命题 | Claim 陈述、适用范围、抽取置信度及其 Evidence；可按关键词搜索 |
| 概念 | 规范概念名、别名、描述、出现次数与来源数量 |
| 实体 | 实体名、受控类型、别名、描述、出现次数与来源数量 |
| 冲突 | 只展示受控来源的冲突候选与待确认差异；允许标记已审阅或保留双方，不自动裁决真伪 |
| 双向链接 | 聚合已确认链接和待确认链接，展示来源、目标、理由与置信度，并复用现有确认/拒绝动作 |

Evidence 行必须展示来源笔记、标题路径或块摘要；点击后打开对应 Notes 文件，并尽可能定位到证据所在标题。所有统计与列表 RPC 都是只读快照，读取工作台不得触发 LLM、全库扫描、索引重建或文件移动。

冲突来源仅限：

1. 语义审核队列中的 `claim_conflict`；
2. 智能整合流程已检测并保存的日期、数字、结论或否定关系差异。

系统不得仅凭两句话语义相似就创建正式冲突。后续结构化冲突检测必须满足同一主体、谓词和适用范围，并将低置信度结果放入审核队列。冲突审阅只改变审核状态，不删除 Claim、Evidence 或原笔记。

双向链接工作台复用现有链接发现数据与确认/拒绝逻辑；已确认链接必须能显示正向与反向来源关系。拒绝建议不会删除笔记正文中已经存在的显式 Markdown 链接。

#### 10.10.1 界面与交互要求

- 复用应用原生三栏：左一保留文件夹树，并在同一滚动导航下常驻四个语义入口；左二复用笔记列表栏；右侧复用正文栏；禁止在 `content-panel` 内创建第二套三栏。
- 点击文件夹时退出语义模式，左二恢复该文件夹的笔记列表；点击语义入口时文件夹树仍然可见，左二切换为对象列表；点击来源笔记时恢复普通阅读模式。
- 语义工作台不设置重复的标题栏入口，四个常驻类别就是工作台入口。
- 左二支持搜索、状态筛选、选中态与独立滚动；右侧详情独立滚动，切换列表项不改变左一类别。
- 命题详情展示全部 Evidence；实体或概念详情展示出现位置与来源块；链接详情展示方向、反向关系和两端笔记；冲突详情展示双方命题、理由、状态及审阅动作。
- 概览只保留能帮助判断编译覆盖度的数字，不引入健康分或真假评分。
- 列表必须提供 Loading、Empty、Error 三种明确状态；错误不得产生未处理 Promise rejection。
- 搜索输入、分段导航、列表行和操作按钮有清晰键盘焦点。
- 浅色、深色、纸张和跟随系统主题下均可读；沿用现有蓝色操作强调色。
- 首屏 RPC 在普通本地知识库中目标 2 秒内返回；列表默认分页，单次最多返回 100 项。

#### 10.10.2 全库语义编译

- 工作台必须同时显示 `Notes/**/*.md` 源笔记总数、已解析文档数、已完整抽取文档数、部分失败文档数和未编译文档数，避免把增量批次大小误认为全库规模。
- 用户可在工作台显式启动“编译全部”。该动作扫描全部 Notes Markdown，而不是复用增量索引待更新列表。
- 全库编译在后台执行，提供当前文件、已处理/总数、成功块、失败块和可理解的错误状态；关闭工作台不取消任务。
- 重复执行保持幂等：未变化且已成功抽取的块跳过；失败块允许重试；不得清空上一版有效语义结果。
- 全库编译不得修改 Notes 正文。LLM 不可用时仍解析全部 Document/Block，并把抽取状态标为待处理。

#### 10.10.3 验收标准

- 工作台能显示当前 `semantic.db` 的真实对象数量，不使用演示数据。
- Claim 仅在存在 Evidence 时显示为正式命题；每条 Evidence 可解析到存在的 Notes 文件与 Block。
- 搜索 Claim、Concept、Entity 时不调用 LLM，且不会修改工作区。
- 冲突为空时明确说明当前没有受控冲突候选；不得把“未检测到”表述成“知识库不存在矛盾”。
- 冲突标记已审阅后可恢复显示历史记录，且不影响原始 Claim/Evidence。
- 待确认双向链接可在工作台中确认或拒绝，操作结果与 Inbox 保持一致。
- 点击 Evidence 或链接端点可打开对应来源笔记。
- 全库 288 篇源笔记场景中，启动“编译全部”后 Document 覆盖数最终等于当前 Notes Markdown 总数（忽略点文件与 `_综述.md`）；失败抽取不得导致 Document 缺失。
- 文件夹树和四个语义一级类别在左一同时可见；实体 / 概念二级切换位于复用后的左二，不回退为顶部页面标签。
- DOM 中不存在位于正文栏内部、同时包含类别栏 / 列表栏 / 详情栏的嵌套语义三栏容器。
- 新增后端单元测试和前端资源契约测试；`uv run pytest` 全量通过。

### 10.11 语义知识治理（v3.8）

通过 Claim 类型门禁并带有 Evidence 的 AI 抽取结果，默认作为当前知识进入语义库，不增加逐条接受流程。用户始终拥有最终编辑权和删除权：可以修改命题陈述、适用范围及 `conclusion` / `hypothesis` 类型，也可以从当前有效知识中删除命题。

删除采用语义层软删除：命题状态改为 `deleted`，默认列表、Wiki 物化和后续查询不再消费该命题，但原始 Notes、Block、Evidence 与审计记录保持不变。用户可以恢复被删除命题。任何编辑、删除、恢复和证据排除操作必须写入追加式审计日志，至少记录动作、对象类型、对象 ID、变更前后值和时间；不得以覆盖日志的方式隐藏历史。

Evidence 默认有效。用户可以排除或恢复单条 Evidence；排除只改变证据边状态，不改写来源笔记。命题的全部 Evidence 都被排除时，该命题不得继续作为当前有效知识展示；恢复任一 Evidence 后可重新生效。

实体支持用户维护别名。别名只建立到规范实体的映射，不改写 Notes 正文，也不得静默合并两个实体。实体合并属于后续显式审核动作，必须展示来源、目标和影响范围，并可从审计记录追溯。

#### 10.11.1 验收标准

- 新抽取的合格 Claim 状态为 `active`，无需人工接受即可出现在“命题与证据”。
- 用户可在右侧详情编辑 Claim 陈述、适用范围和类型；保存后列表与详情同步刷新。
- 用户删除 Claim 后，默认列表不再显示；切换到“已删除”可查看并恢复。
- 编辑、删除、恢复 Claim 以及排除、恢复 Evidence 均不修改 `Notes/` 文件。
- 每次治理动作生成一条不可变审计记录；失败操作不生成半条记录。
- Entity 可添加非空、去重的别名，并在详情中展示。
